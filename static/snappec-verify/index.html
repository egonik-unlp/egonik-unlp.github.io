snappec-verify

Verifica que lo que una spec afirma se sostenga en el sistema real. Convierte la spec en un contrato ratificado de invariantes y corre cinco prongs que intentan romperlo. Los agentes proponen, el código decide, las personas ratifican.

Instalar

El script detecta sistema y arquitectura, descarga el binario, verifica el checksum y lo deja en ~/.local/bin. No necesita Go ni root.

curl -fsSL https://egonik-unlp.github.io/snappec-verify/install.sh | sh

Otro destino: BINDIR=/usr/local/bin antes de sh. Una versión puntual: SNAPPEC_VERIFY_VERSION=<versión>.

A mano

Bajá el .tar.gz de tu plataforma desde la tabla de abajo, descomprimilo y poné el binario en el PATH.

tar -xzf snappec-verify_*.tar.gz
install -m 0755 snappec-verify ~/.local/bin/
snappec-verify --version

En macOS, un archivo bajado con el navegador queda en cuarentena y Gatekeeper no lo deja correr. Se la quitás con:

xattr -d com.apple.quarantine ~/.local/bin/snappec-verify

Llevarlo a un proyecto

En un proyecto Rails dockerizado con snappec, el bootstrap son dos comandos. El código de la app no se toca: lo de verify vive en verification/ y .claude/.

Requisitos:

  • Docker con Compose v2
  • Un proyecto Rails dockerizado, con MySQL o Postgres
  • Claude Code con snappec instalado

1. Instalar verify en el repo

cd <tu-proyecto>
snappec-verify init --snappec

Deja los comandos /verify:*, los agentes y el hook que mantiene a los agentes fuera del contrato, los runs, el baseline y el bank. Sin snappec, snappec-verify init instala el modo standalone.

2. Bootstrap desde Claude Code

/verify:bootstrap

Detecta compose, motor de base, servicio de app y el resto del stack.yaml. Pregunta solo lo ambiguo, escribe el binding y corre la conformance del adapter dentro del compose.

3. Ver dónde estás

snappec-verify status

Cada testing set es una máquina de estados: status dice qué paso sigue y qué falta para darlo.

Los prongs

Cada invariante del contrato se chequea con un oráculo CEL de decimales exactos. Los prongs generan los casos; el resultado queda en records encadenados por hash.

  • P1 Property: generadores con semilla y shrinking de secuencias de operaciones.
  • P2 Bank: edge cases que alguien ya encontró, re-ejecutados en cada corrida.
  • P3 Estático: analyzers sobre el código, calibrados por proyecto, que rutean candidatos a los otros prongs.
  • P4 Sandbox: la app en un compose con la red cercada, sondas de autorización y diff de la base.
  • P5 Volumen: carga y concurrencia con un scheduler determinístico; cada interleaving se puede repetir.
